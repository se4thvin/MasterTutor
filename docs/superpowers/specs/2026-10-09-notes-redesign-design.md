## 1. Goal and scope

A captured note should read like a well-set textbook page. That means:

- a comfortable measure and a clear hierarchy;
- an outline you can steer by;
- math and code that arrive already typeset, with no flash and no client JavaScript;
- provenance one hover away instead of filling the margins.

The person can:

- learn from the note with AI-selected study aids: verbatim key passages, terms with their own defining sentences, cloze cards and cloze quizzes (D54). They are always labelled, always re-extracted from the note's own text, and never mixed into the 1:1 text;
- review cards they chose on an FSRS schedule;
- mark the note up with highlights and comments that survive edits and re-capture;
- find notes again in a library that shows at a glance what each note is.

In scope:

1. **Reader.**
   - Server-rendered blocks.
   - Typography and measure, heading hierarchy, pull-quotes.
   - A sticky outline with scroll-spy and reading progress.
   - Figures with captions and zoom, math, code, activity callouts.
   - Quiet provenance with one fidelity badge.
   - No duplicate title or intro.
   - A glass floating toolbar, focus mode, and a print stylesheet.
2. **Study layer.**
   - Extractive only (D54): verbatim key passages, key terms with their verbatim defining sentences, AI-selected cloze cards that the user adopts, cloze and recall quizzes whose options are all verbatim spans, and the user's own cards.
   - FSRS review of adopted cards, per note and across notes (`/review`).
   - Its own tables; generated by the agent through the single OpenAI wrapper.
   - Exportable, always marked AI.
3. **Highlights and comments.**
   - W3C TextQuote and TextPosition anchoring per block range.
   - Server re-anchoring per note version.
   - Painted with the CSS Custom Highlight API.
   - An orphan tray, per-user scope, and Obsidian export.
4. **Library refresh.**
   - Cards with a cover preview, title, source icon, fidelity badge, reading time and due count.
   - Folder views and sort, Pip empty states, glass chrome.
5. **Reader side of the layout spec (D53b).**
   - The contract, the stored columns, the reader mapping, live updates through `note_layout`, the swap policy, and the manual override.

Out of scope:

- **The layout producer**, both the rules engine and the model call. These belong to the Observer plan (ruling 2). Until it lands, the reader uses the `article` preset spec for any note with no stored spec [NR §6, DD §5].
- **Changing what capture writes.** All reader improvements are display rules over existing blocks (§6.2).
- **The agent's habit of writing "study notes" as commentary blocks.** This is raised as user decision §16 Q1.
- **An FSRS parameter optimiser** [NR §2.1]; v1 uses the default parameters.
- **Cross-user annotation sharing.** Annotations are private (D4).
- **"Highlight → card"** [NR §3.2] is a follow-up (§16 Q4).
- **Native apps and PDF generation services** (R5: print CSS only).

## 2. Binding requirements

| # | Requirement |
|---|---|
| R1 | **Faithful text is never altered.** No reader, layout, study or annotation feature writes to `note_blocks.markdown`. Display rules can hide an exact duplicate or regroup blocks visually, but every block keeps its own element, id and provenance. A hidden echo's provenance moves to the element it duplicates. Exports keep each block body byte-exact. |
| R2 | **AI is always labelled.** Every surface that shows study content carries the AI mark (a sparkle icon plus **"AI-selected"**) and a caption: "Selected by AI from this note's text. Every word shown is from the note." It also gives the model and date. Exports mark AI-selected content in front matter and callouts. Agent commentary blocks (`origin='model'`) carry the AI mark with the label "Agent's note". The study surface uses its own wash token, `--ai-wash`, which faithful text never uses [NR §2.4]. |
| R3 | **Study is separate and extractive only (D54).** Study content lives in `study_*` tables, never in blocks. The model only **selects** spans by reference (segment ids and word indices) and never writes text. Every stored span is `{blockId, start, end, contentSha256, text}`, where `text` is re-extracted by the server from the unedited captured block and must equal `plainOf(markdown).slice(start, end)`. Anything that does not re-extract is dropped. An item is stale once its block's current hash differs. AI-selected cards are **suggested**; only cards the person **adopts** enter FSRS. A person's own cards are `origin: user`, which is their text [ruling 3, D54]. |
| R4 | **One OpenAI path.** Study selection runs in the agent through `createOpenAI`: `store:false`, no identifiers (D37/D38). Page text is wrapped by `wrapUntrusted`. The output schemas hold references only, with no string fields except constrained segment ids. Usage is priced by `usageDelta` and capped per workspace per 24 h. The kill switch blocks selection. web never calls a Responses model (D36). |
| R5 | **Annotations are scoped** to `(workspace_id, user_id)` on every read and write. The agent has no grant on `annotations`. Unknown or foreign ids answer `NOT_FOUND`. |
| R6 | **The layout spec is a closed vocabulary.** `LayoutSpec` contains only enums and booleans, is `.strict()`, and is parsed on every write and read. The renderer maps each value through an exhaustive `Record` onto `data-*` attributes and never interpolates a value into a style, class or CSS variable [DD §2.2–2.3]. `NoteStructure`, the producer's input, carries only enums, booleans and log2-bucketed counts, never text [DD §4.1]. |
| R7 | **Glass only on chrome and the floating layer:** the floating toolbar, the selection pill, the outline rail and popover, menus, sheets and the review bar. All use `<LiquidGlass>` and the `--glass-*` tokens from `fe-sidebar-glass`. Content (blocks, cards, study items, comments) is solid. Never glass on glass. Reduced transparency and `prefers-contrast: more` both make glass solid [NR §5]. |
| R8 | **Lean client.** Markdown, KaTeX and highlight.js run only on the server (web's Node runtime), and the client gets HTML. The KaTeX stylesheet loads only on notes whose HTML contains math. The study panel, review, figure zoom and the annotation layer each load on first use. The note route's first-load JS shrinks: `react-markdown` and the rich-plugin chunk leave the client. |
| R9 | **HIG and D21/D28 motion.** 44 px targets; 4.5:1 text contrast; a keyboard path for every pointer action. `prefers-reduced-motion` turns movement into crossfades. Transform and opacity only. React Bits text effects never touch faithful text [NR §5]. |
| R10 | **Migrations.** `0016_note_reader` (Task 0), `0017_study` (Track B), `0018_annotations` (Track C). They merge in number order. |
| R11 | **Dependencies.** New runtime deps: `ts-fsrs` and `approx-string-match`. They are web server-side only, so the client bundle is unchanged. R1 server rendering also needs `rehype-stringify`. It is the server half of the unified pipeline that `react-markdown` already pulls in, its sibling `hast-util-to-html` is already a transitive dependency, and it adds no client bytes. §16 Q5 flags it for the user. |

**A bug the design must avoid.** `updateBlock` leaves `content_sha256` at the captured hash (`apps/web/lib/server/library/notes.ts`). That hash therefore cannot key a render cache or detect edits. Migration 0016 adds `note_blocks.markdown_sha256`, a stored column generated as `encode(sha256(convert_to(markdown,'UTF8')),'hex')`. It is the one hash of the block's current text. The render cache, study staleness and annotation re-anchoring all use it. `content_sha256` keeps its existing meaning: the captured text's hash, used for provenance.

**Focus mode** [NR §1.7]:

- The app sidebar, outline and margin hide.
- The toolbar hides while scrolling down and returns on scroll up, or on pointer at the top edge.
- Non-focused blocks dim to 35% opacity (an opacity transition).
- Keys, when focus is not in a field:
  - `j`/`k` move the focused block (it scrolls into view centred);
  - `h` highlights the focused block's whole text;
  - `n` highlights it and opens a comment;
  - `F` toggles focus, and Esc leaves it.
- The Aa popover also offers Focus.
- The setting persists per viewer in `localStorage`, guarded by try/catch, because it is a convenience.

**Resume reading** [NR §1.7]: the reader stores the id of the topmost visible block per note in `localStorage` (throttled to one write per second). On open, if that block exists and is not the first block, a glass chip appears under the toolbar: "Resume where you left off". It disappears after 6 s or on scroll. The page never scrolls by itself.

- `blockAdornment(blockId)`: a `ReactNode | null`;
- `selectionActions`: a `ReactNode` inside the selection pill;
- `toolbarItems`: the study and annotate buttons.

Tracks B and C fill these slots through `NotePage`, the one composer, and never edit the shell.

### 6.2 Display rules (pure; `apps/web/lib/notes/present.ts`)

`presentNote(view, spec): ReaderModel` turns blocks into ordered **items**. An item is one of:

- one block with a role;
- a group (a compact run);
- a divider.

Rules apply in order. Every rule has unit tests on the §3 fixture and on hostile input. "Plain text" is `plainOf(markdown)`, defined once in `packages/contracts/src/markdown.ts`. It:

- strips emphasis, code, heading, quote and list markers;
- keeps link text;
- applies NFKC;
- collapses whitespace and trims;
- for rule matching only, lowercases.

| Rule | Condition | Display |
|---|---|---|
| P1 Title echo | The first `heading` among the first 3 blocks whose plain text equals the plain title. | Hidden. The title's tick opens this block's provenance. |
| P2 Lede echo | The first block among the first 5 whose plain text equals the plain lede. | Hidden. The lede line shows `notes.lede` once, and its tick opens this block's provenance. |
| P3 Section rule | A paragraph whose trimmed Markdown is `---`, `***` or `___`. | A short centred hairline with extra space. |
| P4 Inferred subhead | A paragraph made only of `**…**` or `__…__`: one line, ≤ 80 characters, no final `.`, `:` or `;`. | `<p role="heading" aria-level={min(6, lastLevel+1)}>` in small caps. Listed in the outline with `inferred: true`. |
| P5 Compact run | ≥ 4 consecutive paragraphs, each one line of ≤ 40 plain characters, no final `.`, `?` or `!`, no Markdown other than emphasis, same source. A P4 subhead directly before or between runs joins as a label. | `kind: "run"`: CSS columns (`columns: 12rem`) of labelled groups. Each block keeps its element and id. |
| P6 Link row | A paragraph whose content, without its links, is only whitespace or `· \| /`. | A footnote-size row of quiet links with the external glyph. |
| P7 Source divider | The source differs from the previous captured block's, and the note has ≥ 2 sources. | Kind icon or favicon, source title (`untrustedText` at 120 characters), host and capture date. Also an outline group. |
| P8 Agent's note | `type: "commentary"` or `origin: "model"`. | A card with the AI mark and the label "Agent's note". With `commentaryCallout: "collapsed"` it shows the first line and a disclosure (Base UI Collapsible). Its headings render one level under the current section and never enter the outline. |
| P9 Pull-quote | A `quote` that is not an activity, ≤ 280 plain characters, and `pullQuotes` is on. | Title 3 type with a tint rule. Longer quotes are plain `blockquote`s. |
| P10 Activity | A `quote` where `isActivityCallout(markdown)` is true. | Per `activityCallout`: a `card` (glyph, "Interactive activity", and "Open on page ↗" through `safePageUrl`), `inset`, or `collapsed`. |
| P11 Figure | `image`, `figure` or `keyframe`. | Numbered "Figure n" when `figureNumbers` is on. The caption is the block's own text (never invented for `image`). Keyframes show their timestamp. `figures: wide` breaks out to 52rem only when the asset's intrinsic width exceeds 1.3× the measure [NR §1.5]. |
| P12 Display math | `math`, or a block whose HTML contains `katex-display`. | With `math: "display_cards"`: centred on a quiet card and numbered "(n)". Always in a horizontal scroll region. |
| P13 Code | `code`. | A frame with a language label, a Copy button (copies the raw fenced text, byte-exact) and horizontal scroll. |
| P14 Timed | A `transcript`, or any block with `anchor.tStart`, when `transcript: "timeline_rail"`. | A left time rail `[mm:ss]` linking to the source at that time. With `interleaved`, keyframes sit beside their transcript paragraphs at ≥ 1180 px. |

A block's editing, verification and provenance do not depend on its role. Hidden echoes stay reachable through the title and lede ticks.

### 6.3 Server rendering (R1; `apps/web/lib/server/notes/render/`)

`renderBlockHtml(markdown, { allowRawHtml }): RenderedHtml` returns `{ html, hasMath, hasCode }`.

**Pipeline:**

1. `unified()` with `remark-parse`, `remark-gfm` and `remark-math`;
2. `remark-rehype` (`allowDangerousHtml` only when `allowRawHtml`, for captured raw-HTML tables), then `rehype-raw` in the same case;
3. **`rehype-sanitize`** with today's schema; it runs before anything trusted;
4. `rehype-katex` with today's options;
5. `rehype-highlight` with the same 13 languages and `detect: false`;
6. `rehypeReaderTransforms`, our own transforms:
   - external `a` get `target="_blank" rel="noopener noreferrer"`, and `#…` links stay in the tab;
   - `img` survives only when `src` matches `^/api/assets/<uuid>$`, after `asset:` rewriting; it gets `loading="lazy" decoding="async"`, and anything else becomes `<span class="inline-img">Image: alt</span>`;
   - `input` becomes a disabled, labelled checkbox;
   - `pre` gets `tabindex="0"`;
   - `table` gets a scroll wrapper with `role="region"`, `tabindex="0"` and `aria-label`;
7. `rehype-stringify`.

**Cache.** `renderCache` is an in-process LRU keyed by `markdown_sha256 + (allowRawHtml ? ":raw" : "") + ":" + RENDER_VERSION`, bounded to 40 MB of HTML. A hit costs one Map lookup. `RENDER_VERSION` is bumped whenever the pipeline changes.

**Where it runs.** `loadNoteView` (web) renders each block (cache first) and returns:

- `RenderedBlock = NoteBlock & { html, markdownSha256, sourceHtml: string | null }`, where `sourceHtml` renders `originalMarkdown` when the block was edited, for the source pane;
- `NoteView = { note, blocks: RenderedBlock[], sources, layout: NoteLayoutView, katex: boolean }`.

`updateBlock` returns a `RenderedBlock`. The fixture router uses the same functions.

**Client.** `BlockItem` renders `<div className="blk-content" dangerouslySetInnerHTML={{ __html: block.html }} />`. The HTML is sanitised server-side, and an ESLint rule permits `dangerouslySetInnerHTML` only in `block-item.tsx`. Study spans and user cards are plain text (D54). When `view.katex` is true, the reader injects the KaTeX stylesheet once with `import("katex/dist/katex.min.css")`. Fonts load per glyph, so notes without math never fetch KaTeX.

**Reading text.** `readingTextOfHast(tree)` is the server walker. `domReadingText(root)` is the client walker. Both follow the one rule in `lib/notes/reading-text-rule.ts`:

- skip `.katex-mathml`, `[aria-hidden="true"]` and elements with `data-rt-skip`;
- treat `.katex` as one atomic unit whose text is its TeX annotation;
- join list items and table cells with a single space.

A parity test renders 40 fixture blocks and checks that the hast text equals the jsdom DOM text. Annotation offsets are defined over this text (§9).

**Performance.** Rendering 141 blocks cold takes under 60 ms on the bench host (the plan measures it). Warm, it costs only the lookups. There is no hydration cost for block content.

### 7.4 Live updates and the swap policy [DD §5]

**The note event stream.**

- `GET /api/notes/[noteId]/events` is SSE, session- and workspace-checked.
- It LISTENs on `note_changed`, filters to this note, and sends `event: note_layout` or `event: study` with `data: {}`: the event name is the only payload. The client then refetches the affected query.
- It sends a heartbeat every 25 s. The client opens it only while the page is visible.
- No polling. Ids only, as on every channel.

**Swap policy** (`lib/notes/layout-swap.ts`, pure, plus a hook):

- A new spec that arrives while the note is open **applies now** only if all of these hold:
  - the reader has not scrolled past the first viewport;
  - there is no selection, editor, comment composer or open sheet;
  - `document.visibilityState === "visible"`.
- Otherwise it is **deferred**. The current spec stays for this visit, and the stored spec applies on the next open.
- The person's own change from the Layout menu always applies at once, because it is their action.
- An applied swap runs inside React 19.3 `<ViewTransition>` with `startTransition`, one crossfade at `durations.panel`. Scroll stays anchored to the top visible block id.
- Under reduced motion, `::view-transition-*` animations are `none`.
- There is no "layout updated" affordance [DD §9 Q4 recommendation].

## 8. Study layer: extractive only (D54, R3, R4) [NR §2 as amended by D54]

**D54 overrides NR R4's generative items.** The model never writes text. It only **selects spans** of the note's own captured text. Each item is one of the following:

- a summary of verbatim key passages;
- a term plus its verbatim defining sentence;
- a cloze card over a verbatim sentence, where the answer is the exact deleted span;
- a quiz item that is a cloze or recall question, where every answer and every multiple-choice option is a verbatim span of the same note.

There are no invented distractors, no explanations and no prose questions. The server re-extracts every span and drops anything that does not match. The label reads **"AI-selected"**. The person can still write their own cards (`origin: "user"`). These are their words, never the model's.

### 8.1 Span model (`packages/contracts/src/study-spans.ts`, pure, shared by agent and web)

- **Study text.** A block's study text is `plainOf(block.markdown)` (§6.2).
- **Eligible blocks.** A block is eligible only if all of these hold:
  - its origin is captured (`CAPTURED_ORIGINS`);
  - `edited = false`, so `markdown_sha256 = content_sha256`, the captured text's hash;
  - its type is `paragraph`, `list`, `quote` (not an activity) or `transcript`;
  - it is not a title or lede echo.

  User edits, agent commentary, activities, code, math, tables and media are never study sources.
- **Segmentation.** `segmentBlock(text)` splits study text with `Intl.Segmenter(…, { granularity: "sentence" })` into **sentences**. Each sentence has `{ start, end }` offsets with trimmed whitespace. Each sentence is split again with `granularity: "word"` (word-like segments only) into **words** with offsets. These are built-in Node and browser APIs with no dependency. Segment ids are `b<n>.s<k>`, where n is the block's index in the input and k is the sentence index.
- **Span.** A span is `{ blockId, start, end, contentSha256 }`, with character offsets into that block's study text. A span stored by the server always carries `text`, which is exactly `studyText.slice(start, end)`. The server fills it by re-extraction, and nothing else may.

### 8.2 Item kinds (`packages/contracts/src/study.ts`)

```ts

  z.strictObject({ kind: z.literal("passage"), passage: Span }),                 // a verbatim key passage (1–3 sentences, one block)
```

| Item | Limit |
|---|---|
| passages | 3–6 |
| terms | ≤ 15 |
| cloze cards | ≤ 30 |
| quiz | 5–10 |

### 8.3 Two-stage selection (agent, `apps/agent/src/study/`)

Models cannot count characters, so selection runs in two small structured calls. Their outputs are **references only**: segment ids and word indices, never text.

1. **Select** (`study-select.ts`).
   - **Input:** the eligible blocks' sentences, one per line, as `[b12.s3] <sentence>`, grouped per source in `wrapUntrusted(origin, …)`. Sentences of unverified blocks are tagged `[b12.s3?]`.
   - **Input cap:** 100,000 characters, taken in order. `blocks_used` and `blocks_total` record any cut.
   - **Output** (`SelectReply`, strict):

     ```
     { passages: [{ from: SegId, to: SegId }]   // same block, ≤ 3 sentences
       definitions: [SegId], clozes: [SegId], quiz: [SegId] }
     ```
2. **Mark** (`study-mark.ts`).
   - **Input:** only the selected sentences, word-indexed: `[b12.s3] 0:When 1:in 2:the 3:Course …`.
   - **Output** (`MarkReply`, strict):

     ```
     { terms: [{ seg, words: [i, j] }], blanks: [{ seg, words: [i, j] }],
       options: [{ seg, distractors: [{ seg, words: [i, j] } ×3] }] }
     ```

     Distractors are word ranges in *other* selected sentences, of the same grammatical kind as the blank.
3. **Re-extract and verify** (`study-verify.ts`, pure). For every reference:
   - The segment id was sent, its block still has the `content_sha256` it was sent with, and the block is unedited.
   - Word indices are in range and `i ≤ j`.
   - The span's `text` is re-extracted from the study text; it is never taken from the model.
   - Blank rules: 1 ≤ words ≤ 60% of the sentence, and the blank is not stop-words only (a fixed list of 80 English stop words).
   - A term lies inside its definition sentence.
   - Options: 3 distinct distractors, each with a different `matchKey` from the answer and from each other, none overlapping the answer's sentence.
   - Anything that fails is **dropped**, never repaired. When no passage survives, the set fails with `invalid_reply`.
   - The verifier re-checks `span.text === plainOf(block.markdown).slice(start, end)` for every span before writing. A violation throws, so a bug can never store non-verbatim text.

Common call settings:

- `MODELS.study = "gpt-6.1-sol"` through `createOpenAI` (`store:false`);
- `maxOutputTokens` 3,000 per stage, a 60 s timeout per stage;
- usage priced by `usageDelta` and summed.

## 9. Highlights and comments (R5) [NR §3]

### 9.1 Contract (`packages/contracts/src/annotation.ts`; W3C-compatible)

```ts
export const ANNOTATION_COLORS = ["yellow", "green", "blue", "pink", "purple"] as const;
export const ANNOTATION_STATES = ["anchored", "fuzzy", "orphaned"] as const;
export const TextPoint = z.strictObject({ blockId: Uuid, blockSha256: Sha256Hex, offset: z.number().int().nonnegative() });
export const TextQuote = z.strictObject({ exact: z.string().min(1).max(4000), prefix: z.string().max(32), suffix: z.string().max(32) });
export const AnnotationTarget = z.strictObject({ start: TextPoint, end: TextPoint, quote: TextQuote });
export const Annotation = z.strictObject({
  id: Uuid, noteId: Uuid,
  motivation: z.enum(["highlighting", "commenting"]),
  color: z.enum(ANNOTATION_COLORS),
  body: z.string().trim().min(1).max(4000).nullable(),      // the comment
  target: AnnotationTarget,
  state: z.enum(ANNOTATION_STATES),
  createdAt: IsoDateTime, updatedAt: IsoDateTime,
});
```

- Offsets are in **reading text** (§6.3).
- `start` and `end` can be in different blocks, which must be in note order. A block comment with no selection targets the block's whole reading text.
- `motivation: commenting` always has a body. `highlighting` may have one.

**Table `annotations`** (migration 0018):

- columns: `id`, `workspace_id`, `user_id` → user cascade, `note_id` → notes cascade, `motivation`, `color`, `body` (check ≤ 4000), `target` jsonb, `state`, `anchored_version` (the note's annotation-anchor version, below), `created_at`, `updated_at`;
- index on `(note_id, user_id)`;
- the agent is excluded in `grants.sql`.

Limits: 2,000 per user per note (`too_many`); `exact` ≤ 4,000 characters.

### 9.2 Server re-anchoring (`lib/server/annotations/reanchor.ts`) [NR §3.1]

Re-anchoring runs on the server, once per **note text version**. That version is `notes.text_version`, a hash of the ordered `(id, markdown_sha256)` pairs. It is computed in SQL by `string_agg` on read; the plan measures it, and it is cheap.

`notes.annotations.list` loads the viewer's annotations. For each one whose `anchored_version ≠ text_version`, it re-anchors and persists the new `target`, `state` and `anchored_version` in one statement per changed row, so the next list is a pure read.

`reanchor(target, blocks)` is pure. `blocks` is `[{ id, markdownSha256, text }]`, where `text` is the reading text from the render cache.

1. **Exact.** The start and end blocks still exist with the same `blockSha256`, and the text at the offsets equals `exact` → `anchored`.
2. **Hash move** (re-capture with identical text under a new id). Find blocks whose `markdownSha256` equals the stored start and end hashes, keep the relative offsets → `anchored`.
3. **Context.** Search the concatenated note text (blocks joined by `"\n\n"`, with an offset map) for `exact` near the old position. Score each occurrence by prefix and suffix agreement, and take the best unique one → `anchored`.
4. **Fuzzy.** `approx-string-match` (Myers) for `exact`, with max errors `min(32, ⌊len/4⌋)`, tie-broken by prefix and suffix score and nearness → `fuzzy`. The reader shows a small "Re-attached" badge on the card.
5. **Otherwise** → `orphaned`. The target is kept for the record.

Property tests (fast-check, dev only) check that:

- any edit outside the quote keeps an annotation `anchored`;
- re-capturing identical text under new ids keeps it `anchored`;
- a single-character typo fix inside the quote yields `fuzzy`, never `orphaned`.

### 9.3 Painting and hit-testing (`highlight-layer.tsx`)

- **Painting.** The layer uses the **CSS Custom Highlight API**: one `Highlight` per colour (`CSS.highlights.set("mt-hl-yellow", …)`), built from ranges that `domReadingText` maps from offsets to DOM positions. CSS: `::highlight(mt-hl-yellow) { background-color: var(--hl-yellow) }`. Background only; Firefox ignores `text-decoration` here [NR §3.1].
- **No DOM mutation.** React's markup, server HTML and copy-paste of faithful text stay untouched.
- **Repaint.** One `requestAnimationFrame`-coalesced repaint whenever annotations or block HTML change.
- **Hit-testing.** On `pointerup` with no selection, `document.caretPositionFromPoint` (or `caretRangeFromPoint`) is compared against painted ranges and opens that annotation's card.
- **Keyboard path.** The comments panel lists every annotation in order. Each block with annotations also gets an adornment button, for example "2 highlights, 1 comment".
- **Colours.** The `--hl-*` tokens are tuned so body text stays ≥ 4.5:1 in light and dark. Colour is never the only signal: cards name the colour, and adornments count highlights.
- **No API.** Without `CSS.highlights`, annotations are listed but not painted, and a one-time note says so. There is no DOM-wrapping fallback.

### 9.4 Comments UI and orphan tray

- **Wide.** Comment cards live in the margin, aligned to their target's top block. They are stacked by `stackCards(anchors, heights, gap)` (pure, about 30 lines) so they never overlap. Each card shows:
  - the quote (2 lines, clamped);
  - the comment as plain text (`white-space: pre-wrap`, never Markdown);
  - a relative time;
  - Re-attached when `fuzzy`;
  - a ⋯ menu with Edit, Change colour and Delete.
- **Medium and compact.** Count chips open a sheet with the same cards.
- **Editing.** ⌘↩ saves; Esc cancels and asks when the comment is dirty. Saves are optimistic: a failed save restores the card with an inline error. Delete shows an undo toast for 5 s (`SwipeToast`).
- **Orphan tray** ("Couldn't place"). A button in the Annotate popover, with a count, opens a sheet. Each orphan shows its quote and comment, and offers **Re-attach to selection** (select text, then press it) or Delete. Orphans are never silently deleted.

## 10. Export (Obsidian) [NR §3.3, §2.4]

**The note file** (`<title>.md`).

## 14. Security

| Threat | Control |
|---|---|
| Server-rendered HTML carries an XSS payload | Sanitise runs before KaTeX and highlight, with the schema unchanged. Our transforms run after sanitise and only restrict further. The existing hostile-Markdown tests are ported: scripts, handlers, `javascript:`, third-party images, raw-HTML tables, `<input>` text fields, and SVG.
